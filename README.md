# PaySense 💳
### Product analytics for payments, delivery experience and customer satisfaction

PaySense is an end-to-end product analytics portfolio project built on the public **Olist Brazilian E-Commerce Dataset**. It explores how payment method, delivery performance and order value relate to customer satisfaction, and turns the results into a testable product recommendation.

**Tools:** Python · SQL · DuckDB · dbt · Pandas · NumPy · statsmodels · SciPy · Streamlit · Plotly

> **Portfolio disclosure:** Olist is a third-party e-commerce dataset used as a proxy product environment. PaySense is an independent learning project, not a Wise product or an analysis of Wise customer data. Observational associations are not causal effects. The experiment shown in the dashboard is simulated, not a real product test.

## The product question

If a product team wants to reduce poor customer experiences, where should it intervene first: payment flows or delivery communication?

The analysis initially surfaced an apparent difference in voucher cancellation rates. Investigating time coverage and missing approval timestamps showed that the impression was strongly affected by an unusual late-2018 period. The project therefore reports a more consistent **January 2017–July 2018** baseline and keeps the excluded period visible in a data-quality investigation.

## Key findings

- **Delivery performance is strongly associated with satisfaction.** In an adjusted logistic regression over **89,230** baseline delivered and reviewed orders, late delivery had an odds ratio of **16.91** for a low (1–2 star) rating (95% CI **15.96–17.92**), controlling for payment method and log order value. This is an association, not an estimate of causal impact.
- **Low-rated orders were approximately 12.99%** of the 89,230-order analytical population; the mean review score was **4.1457 / 5**.
- **Payment conclusions depend on the analysis window.** An apparently high voucher cancellation rate in the full dataset was concentrated in August–October 2018. Using the January 2017–July 2018 baseline, the voucher cancellation rate was approximately **0.47%** versus **0.55%** for credit-card-only orders. Differences in this observational dataset should not be presented as causal.
- **A practical next step is to test proactive delivery-delay messages.** The included experiment illustrates random assignment, power and statistical analysis with *synthetic outcomes*. Its estimated effect is **not real customer evidence** and does not justify rollout.

## Data pipeline

```text
Olist raw CSV files
       │
       ▼
dbt staging models (orders, payments, reviews)
       │
       ▼
dbt intermediate models (order-level payment and review aggregates)
       │
       ▼
fct_order_experience (one row per order)
       │
       ├──► mart_product_kpis (monthly baseline KPIs)
       │
       ▼
Streamlit + DuckDB + Pandas + Plotly
```

The pipeline uses automated dbt tests for keys, nulls, expected categorical values and model grain. In a reconciliation against the original Python-derived `order_analysis` data, **99,441 orders** matched on payment method, total payment, review score and delivery-delay days. Six baseline KPIs also matched after applying equivalent filters.

## Run locally

### 1. Get the data

Download the **Brazilian E-Commerce Public Dataset by Olist** from Kaggle and extract the relevant CSVs into `data/raw/`:

- `olist_orders_dataset.csv`
- `olist_order_payments_dataset.csv`
- `olist_order_reviews_dataset.csv`

Dataset page: https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce

Additional Olist source CSVs may be present but are not required for the three staging models described above. Check the dataset licence and terms before redistributing its files.

### 2. Create the analytics environment

Python 3.13 is recommended for the dbt environment used during development.

```bash
python3.13 -m venv .venv-dbt
source .venv-dbt/bin/activate
python -m pip install -r requirements-dbt.txt
```

### 3. Build and test the dbt models

```bash
cd dbt_paysense
dbt build --profiles-dir .
cd ..
```

The project profile writes its DuckDB output to `paysense_analytics.duckdb` in the project root. Run from `dbt_paysense/` so the existing relative file paths in the model SQL resolve as expected.

### 4. Generate the simulated experiment outputs

```bash
python -m pip install -r requirements.txt
python experiments/experiment_001.py
```

### 5. Build the legacy comparison database (current compatibility requirement)

The **Insights → Data Quality Monitor** section of the current app queries legacy `paysense.duckdb` tables (`orders` and `order_analysis`). Those must be available locally. The original project generated them with its exploratory/analysis scripts. The new dbt pipeline **does not yet replace that anomaly-monitor dependency**.

Do not assume the app is deployable with only `paysense_analytics.duckdb`; either reproduce the legacy database with the project's original scripts or migrate the remaining anomaly queries before public deployment.

### 6. Launch Streamlit

```bash
python -m streamlit run dashboard/app.py
```

To run Streamlit in a separate environment, install `requirements.txt` there instead. Close Streamlit before rebuilding a database file if you encounter DuckDB file-locking errors.

## Reproducibility and validation

- **Grain:** the final fact table is one row per `order_id`; payment and review rows are aggregated before joining.
- **Order reconciliation:** original and dbt order-level datasets had matching coverage and four compared fields across 99,441 orders.
- **KPI reconciliation:** six common baseline metrics matched across pipelines, including 89,230 reviewed/delivered orders, a 12.9867% low-rating rate and a 4.1457 average rating.
- **Population caveat:** the monthly KPI mart requires delivered orders with a review, delivery-date information and non-null payment totals. The interactive dashboard can additionally filter payment methods, date and order value; therefore not every figure is calculated over exactly the same subset.

Run the validation scripts with both databases available:

```bash
python validation/reconcile.py
python validation/validate_kpis.py
```

## Experiment design (EXP-001)

**Hypothesis:** Sending proactive warnings and updated estimated delivery times to customers identified as at risk of delay may reduce low ratings.

- Control: standard order-tracking experience.
- Treatment: proactive warning, revised ETA and support option.
- Primary outcome: low-rating rate, defined before assignment.
- Guardrails: complaint and support-contact rates, notification opt-outs and delivery completion.

The demonstration generates synthetic groups and outcomes from assumed rates, then tests the difference. Its p-value and confidence interval describe **the simulated data only**. A real experiment would require an operational risk trigger, ethical and reliable assignment, outcomes observed in production, guardrail measurement and an agreed decision threshold.

## Limitations

- Observational data cannot identify causation, and unobserved factors may confound associations.
- Reviews are not available for every order; review-based measures describe the observed subset.
- Delivery delay is computed by calendar date against the recorded estimate.
- Voucher cancellations and missing approvals in late 2018 warrant investigation, not an assumed explanation.
- The Olist dataset is historical and is not Wise transaction data.
- A public deployment needs packaging work: generate or supply permitted datasets, eliminate or rebuild the legacy DB dependency, and verify file paths and resource limits.

## Suggested product recommendation

**Prioritise a real experiment for proactive delay communication**, rather than changing voucher payments on the basis of an anomalous unadjusted cancellation statistic. Define eligibility and primary metrics before launch; monitor guardrails and make a rollout decision only from real-world results.
